# ULTIMATE LOOP — Survival-First Development Method

Timestamp: **2026-08-11 20:29 JST**

Canonical motto added: **2026-08-11 20:33 JST**

Status: `NAMED / METHOD_CANONICALIZATION`

Formal name: **ULTIMATE LOOP**

ULTIMATE LOOP is the development method that combines the three survival loops with creator-independent continuity and regeneration.

It is not a single implementation, framework, runtime, or product.
It is the method used to decide what deserves to exist, which concrete implementation deserves to survive, when a promoted implementation should be replaced, and how the human-important outcome remains recoverable after implementations, providers, tools, or even the original creator disappear.

## Canonical motto

> **百万回死んでも残るものだけ、作るべきである。**

Operational form:

> **百万回殺せ。なお立つものだけ作れ。**

This language applies to ideas, requirements, architectures, implementations, dependencies, and promoted software occupants — **not to people**.

The method deliberately makes software disposable so that human-important outcomes do not have to be.

## The three loops

### Loop 1 — Raison d’être Destroy Loop

Question:

> Should this responsibility exist at all?

Kill the need first.

For each desired outcome:

`DROP → EXTERNALIZE → COMPOSE → MANUAL_BOUNDED → GLUE → IRREDUCIBLE_BUILD`

Only the minimum responsibility that cannot be killed under current evidence may proceed.

Core rule:

`NO SURVIVAL, NO BUILD.`

### Loop 2 — METEOR CRUCIBLE

Formal name: **METEOR CRUCIBLE — Reality Survival Loop**

Question:

> Which concrete implementation can actually survive reality best?

Materialize the strongest existing/external composition and the smallest justified custom/glue candidate.
Attack them with the same frozen workload, evidence requirements, authority boundaries, destructive cases, recovery obligations and whole-life-cost criteria.

Only the concrete implementation rows that survive may be promoted.

### Loop 3 — DARWIN ARENA

Formal name: **DARWIN ARENA — Continuous Replacement Survival Loop**

Question:

> Does the current promoted occupant still deserve its slot now?

Every promoted implementation lives in a Movable Frame.
When a credible challenger appears because technology, price, provider behavior, security, user burden, law/procedure, runtime or real-world evidence changes, the incumbent and challenger receive the same inherited workload and known death causes.

Possible results:

- incumbent survives;
- challenger replaces incumbent;
- hybrid recomposition survives;
- partial replacement;
- both die and necessity is reopened.

No implementation gains a permanent right to exist.

## Creator-independent continuity

ULTIMATE LOOP is bounded by the **PHOENIX LINEAGE** continuity goal.

The final protected subject is not code.
It is not a provider.
It is not the original creator.

The protected subject is the human-important outcome and the ability to reconstruct the material evidence, state, meaning, decisions, recovery path and known failure history needed to reproduce that outcome when it matters.

Therefore:

`IMPLEMENTATION MAY DIE`

`RESPONSIBILITY MAY MOVE`

`PROVIDER MAY DISAPPEAR`

`CREATOR MAY BE ABSENT`

but the system should preserve enough lineage and canonical material for a future human/tool/AI to determine:

- what mattered;
- why it mattered;
- what had to be preserved;
- what previously failed and why;
- what authority boundaries remain;
- how to recover the protected material;
- how to rebuild the outcome using the best currently available means.

## Development flow

`WISH / PROBLEM / EVENT`
→ `PROTOTYPE SWARM`
→ `LOOP 1: RAISON D'ÊTRE DESTROY`
→ `SURVIVING RESPONSIBILITY`
→ `REALITY CANDIDATES`
→ `LOOP 2: METEOR CRUCIBLE`
→ `PROMOTED SURVIVOR`
→ `MOVABLE FRAME`
→ `REAL USE`
→ `MATERIAL FAILURE / BETTER CHALLENGER / ERA CHANGE`
→ `LOOP 3: DARWIN ARENA`
→ `SURVIVE / RECOMPOSE / REPLACE / DIE`
→ `PHOENIX LINEAGE PRESERVES MEMORY + REGENERATION CAPABILITY`
→ repeat.

## Era-change rule

ULTIMATE LOOP explicitly treats technological and social change as an expected input, not an exceptional migration project.

A current implementation may be replaced when materially better alternatives emerge because of:

- new AI/model capability;
- new OS/platform capability;
- new API/OSS/SaaS/tooling;
- lower cost or lower operator burden;
- provider degradation or disappearance;
- security/privacy improvement;
- law/procedure/program change;
- improved evidence/recovery capability;
- better composition that removes custom code;
- a new real-world failure class.

`OLD != BAD`

`NEW != GOOD`

Only comparative survival evidence decides.

## Human priority rule

Programs are disposable.
People are not.

ULTIMATE LOOP may repeatedly kill, replace, externalize, shrink, expand or remove software components.
That disposability exists to protect the opposite property at the human layer:

> The person should be able to obtain what matters most, at the moment it matters most, and recover it even after the original implementation is gone.

The method optimizes for human outcome continuity, not code continuity.

## Memory rule

Every survivor inherits the useful memory of the dead:

- frozen workloads;
- failure/autopsy records;
- rejected alternatives;
- unresolved UNKNOWNs;
- authority boundaries;
- evidence/recovery requirements;
- migration assumptions;
- predecessor lineage.

`NEW OCCUPANT != NEW MEMORY.`

## Method invariant

**Kill the need. Kill the implementation. Keep killing the incumbent when reality changes. Preserve the human-important outcome and the memory required to regenerate it.**

That full method is **ULTIMATE LOOP**.
